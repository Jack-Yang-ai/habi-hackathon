# Habi 前端与 Step Studio 交付

产品名已确定为 Habi。前端是 React 19、TypeScript、Vite 6。正式角色使用用户提供的透明 PNG 原图，餐食演示插画为本地 SVG；没有远程图片或字体依赖。

## 本地实现

`apps/studio` 是本次在本机独立实现并接入真实本地 API 的主前端，不是从 Step Studio 下载的源码。Studio 工程作为单独的原型路线保留，不能混淆来源。

在仓库根目录：

```bash
npm install
npm run dev
```

开发页面使用 `http://localhost:5173`，Vite 将 `/api` 与 `/media` 代理到 `127.0.0.1:8787`。`npm run build` 产出 `apps/studio/dist`，本地 API 的 8787 服务直接提供该目录。

正常模式初始没有餐食记录，所有设备连接、暂停和模型配置都读 `/api/state`。历史虚拟故事与确认事件仍保存在服务端，当前首页不展示填充故事或重复确认动态。客户端不会在服务错误时回退到示例。

演示从“设备与设置 → 看看演示”进入，持续显示演示横幅。也可以显式访问 `/?demo=1`。示例只驻留在内存，不调用写入接口、不上传照片，退出后重新加载真实服务状态。为了让分析页可以被真实走一遍，演示现在带一份跨 6 天的示例餐食，含明确标注的示例热量与营养素；每餐都带“演示数据，不是真实识别结果”，判读方式与真实数据一致，但不代表识别能力。

## Habi 视觉与交互（第五轮：对话即首页）

2026-10-16 落地 Codex 最后确认的方向：暖深色工作台 + 常驻对话画布。上一轮的暖纸面 `#FAF8F4` 整套主题被替换，`styles.css`、`habi.css`、`presence.css` 合并为一个 `theme.css`。

- **暖深色**：背景 `#16120F`，卡面 `#221C17`，正文 `#F5EFE6`，次要 `#C6BAAC`，强调橙 `#FF9E5E` 只用于主操作与进行中的量。营养色固定为碳水 `#EFB25A`、蛋白质 `#D98C6A`、脂肪 `#8FA9C9`，只做色点与数字，不铺整行底色。
- **字体**：数字与拉丁使用自带 `@font-face` 的 Manrope 可变字重（`public/fonts/manrope-latin-wght.woff2`，SIL OFL，24 KB，无远程依赖），中文回落到系统 `PingFang SC / Noto Sans CJK SC / HarmonyOS Sans SC`。整套只有 4 个字号与 2 个字重，撤掉上一轮的 Georgia 衬线标题与宋体混排。
- **首页就是对话**：顶部只有一枚 44px 的小 Habi、一行状态和右侧三个入口（分析、设置、资料）。没有大角色、没有独立欢迎页、没有「记下一餐」按钮。首日为空时只有两句话；有待确认餐时它就是时间线里的一张卡。
- **一餐一张卡，状态原地变化**：同一张卡从「待你确认」到「已收好」，确认后收成一行。补充食量在输入框上方固定托盘里完成（全部 / 一半 / 一点 / 没吃），聊天里说出比例时托盘同步预选，仍需用户点确认才调用一次原子 `/confirm`。
- **拍照入口收进输入框的 ＋**：拍一张（`capture=environment`）与从相册选两项，不再有独立的记录入口。
- **独立分析页**（用户明确要求保留）：日 / 近 7 天切换；热量环与区间、营养素结构与占比、近 7 天柱状（含参考线与「有记录但未估算」的区分）、进食时间带、当天的餐食清单（合并原「饮食」页）、以及带依据的 Habi 观察。空状态如实说明缺什么，不补数字。
- **热量参考值**：优先用资料里用户自己填的 `calorieTarget`；没填时按 Mifflin–St Jeor（静息 × 1.35，管理体重留 400 kcal 余量）推算，并明确写“参考值按资料推算”。低于静息值不采纳，页面持续标注这是参考、不是医嘱、也不代表必须吃到。
- **Habi 会动一点**：`tools/habi-avatar.py` 从用户提供的原图派生 6 帧表情（睁眼、闭眼、左看、右看、上看、开心），脚本只做眼部区域的行内插值与绘制，不重绘角色、不改原图字节。前端按“平时呼吸 + 随机眨眼 + 偶尔看旁边 + 收到照片开心一下 + 说话时抬起视线”组合，支持减少动画。仍是 2D 图，没有 3D 或 Rive。
- **返回行为**：分析页的返回箭头、托盘的关闭、＋ 菜单都带 `data-habi-collapse`，网页面板用 `[role=dialog]`，与 Android 宿主的返回顺序（弹层 → 托盘/菜单 → 分析页 → 退出）一致。

卡片按对象与状态区分：时间线待确认卡（照片主导、暖描边）、确认后的一行收据、输入框上方的补充托盘、分析页的餐食行、估算详情页。圆角 12–18px，细边界，不使用模糊投影或装饰光效。餐食详情页保留整份与按食量换算的两组数字，并把碳水 / 蛋白质 / 脂肪占比列出来。

正式角色 `apps/studio/public/habi/character-front.png` 为用户提供的透明 PNG 原文件，保持原始字节和透明通道。派生表情帧放在 `public/habi/*.webp`，由脚本可再生。背屏预览入口仍在设置；页面中的点阵图是设计预览，不把网页动画视为实机上屏证据。

底部是两个 Tab：「对话 / 分析」。餐食清单并入分析页，不再有只重复计数的独立页面，也不再用虚拟故事或重复的确认动态填充首页。两个 Tab 各自保留滚动位置；对话默认贴住最新一条，用户手动上滑回看后切走再回来会回到原来的位置。切换 Tab 用 `history.pushState` 记一步，Android 返回键先关弹层、再关托盘与 ＋ 菜单、然后从分析页回对话页、最后才退出。

拍照入口是输入框左侧**一个 ＋**：点开是一个列表，两项「打开相机 / 上传照片」。打开相机在真机上调用系统相机应用（`MediaStore.ACTION_IMAGE_CAPTURE` + 可写 MediaStore 目标），有取景预览，拍完把 URI 交回页面走同一条上传与卡片流程；上传照片直接打开系统 picker。原生宿主不再插入自己的二次选择弹窗（旧版对两种来源都会再弹一次「拍一张 / 从相册选择」），改为按 WebView 的 `isCaptureEnabled` 分流。语音唤醒与宿主自带的静默拍照仍走原来的 Camera2 单张路径，两条路径互不影响。

首日没有任何记录时，首页不再是空荡的空白：Habi 放大到 104px 居中，配一句问候、一句引导和一个指向 ＋ 的提示气泡；一旦有第一条记录就回到对话时间线。

两种撤回，规则不同，因为有意义的时间尺度不同：

- **说过的话**：两分钟内，你自己那条消息下会出现一个安静的「撤回」，点下去这句话和 Habi 对它的回复一起从对话里消失，并在服务端留一条只记录事实、不记录内容的 `chat.recalled` 事件。撤回只动聊天，绝不改动任何一餐——食量、确认状态、版本号都不受影响；超过两分钟服务端返回 409，界面也不再显示这个入口。长按/滑动之类的隐藏手势没有采用，代价是它只出现在两分钟窗口内，且只出现在用户自己的消息下。
- **记录下来的那一餐**：用户主动建立的记录**随时**可以撤回，不受时间限制，已经确认的也可以。两个入口：餐食详情页底部安静的一行「撤回这一餐」，以及分析页「这一天的餐食」每一行右侧的小垃圾桶图标（44px 热区，`aria-label` 带餐名）。两处都先在**原地**展开一次确认（说明会删掉什么、恢复不了），再点「撤回」才真的执行——不做左滑删除这类隐藏手势。撤回会一起删掉：这一餐、它的原始照片文件、确认时生成的动态、以及 Habi 那侧指向它的食量提案；**用户自己说过的话保留**，可以再单独撤回。服务端只留一条不含内容的 `meal.recalled` 事件（来源、是否已确认、照片数与提案数）。接口不按来源设门槛——自动拍到的餐一旦被用户确认，也是用户自己的记录，同样应该撤得掉；如果不希望这样，说一声我再收紧。

对话可显式绑定 `mealId`，历史按全局或具体餐隔离。明确比例表达只生成可回读的 `mealProposal`，原句保留为候选备注；复杂、否定、疑问或多餐归属不明时不猜比例。候选明确显示「待你确认」，用户点确认才原子保存食量、备注与确认事件；任何聊天或动态回复均不再直接修改餐食。有估算时只按整餐食量比例换算，备注并不代表按单个食物重新计算。

交互参考 [Apple Tab bars](https://developer.apple.com/design/human-interface-guidelines/tab-bars)、[Sheets](https://developer.apple.com/design/human-interface-guidelines/sheets) 与 [Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)：对话默认贴住最新一条，用户上滑回看时不抢滚动位置；弹层用单一取消入口，设置进入资料后返回设置；个人资料、食量备注和分对话的未发送草稿在当前页面内存暂存。主要控件热区至少 44 CSS px，表单输入 16px，并根据 visualViewport 更新可见高度。原生 WebView 按系统 fontScale 设置文字缩放；前端用 390×844 与 320×640 两档逐元素核对热区、对比度与横向溢出。TalkBack 与系统字体的真机效果不以此替代。上述是 Web 界面的交互适配，不是 iOS 原生组件或 iOS 真机验收。

Android 宿主的正常页面隐藏重复开发顶栏，连接配置收进设置；服务页面无法加载时仍保留原生连接入口，判定用 `[data-habi-app]` 而不是会随改版变化的样式类名。主屏和弹层预留系统状态栏、手势区与 IME 高度。宿主的状态栏 / 导航栏与根视图跟着换成同一暖深色（`#16120F`）并关掉浅色状态栏图标，不再在深色页面顶部留一条亮边。系统返回先交给键盘，再关闭弹层；弹出层收完后从分析页回对话页，最后才退出 App。

首页右上角头像、设置页资料行可填写昵称、性别、年龄、身高、体重、饮食目标及忌口备注。全部选填，正常模式通过 `/api/profile` 保存在本地服务，支持修改与清空；演示模式仅保留在内存。表单不会把个人资料送到模型或开启采集。

## 已连接的行为

| 交互 | 接口 | 边界 |
| --- | --- | --- |
| 查看记录、配置与设备状态 | `GET /api/state` | 无服务时显示未连接，不编造设备状态 |
| 选择照片 | `POST /api/capture` | multipart `image`、规范 `metadata`；JPG/PNG/WebP，最大 8 MB |
| 明确选择实际份量、备注 | `POST /api/meals/:id/correction` | 未知份量保留 `null`，不会默认整份；四分之一准确标注为“约四分之一” |
| 确认一餐 | `POST /api/meals/:id/confirm` | 携带版本、食量、备注时原子更新和确认；冲突需回读复核 |
| 分析手动照片 | `POST /api/meals/:id/analyze` | 只有模型已配置且用户勾选逐张发送同意，才带 `consentToUpload:true` 调用 |
| 原位对话与餐食候选 | `/api/chat` | 显式 `mealId` 上下文、消息幂等、候选随消息持久化；规则回复明确标注 |
| 撤回自己刚说的话 | `POST /api/chat/messages/:id/recall` | 只允许 `role=user`、两分钟内、且只删除消息本身与它的回复；不触碰餐食记录 |
| 撤回一餐记录 | `POST /api/meals/:id/recall` | 用户主动建立的记录随时可撤回：删除该餐、它的照片文件、确认时生成的动态，以及指向它的 Habi 提案；用户自己说过的话保留 |
| 开启/暂停自动拍照与识别 | `POST /api/device/pause` | 开关旁说明自动触发的首张照片会送 Step 视觉检查；已拍队列仍可补传，暂停不代表关闭 IP 响应 |
| 受保护服务连接 | `POST /api/session` | 口令不写 localStorage；由服务端 HttpOnly cookie 维持连接 |

图中整份热量与按用户食量换算的热量分别映射 `plateCalorieRange`、`consumedCalorieRange`，有值时也明确标注是估算。未配置模型时只显示“热量尚未估算”。

第五轮在合约与存储层补了营养与参考值：`Meal.analysis.macros` 存整份估算的 `proteinG / carbsG / fatG`（可为 null），`Meal.consumedMacros` 只按用户确认的食量换算；`PersonalProfile.calorieTarget`（800–6000，整数，可为 null）是用户自己填的每日参考。旧的已保存档案与旧餐食回读时为 null，界面显示“营养素未估算”，不推测补值。视觉模型提示词要求整份宏量营养，缺项或格式不合法时清空为 null，没有食物时同样清空。

## 用餐线索与安静提醒

前端复用共享 contract 的 `signals`、`reminder`、`device.captureMode`、`captureWindow` 与 `captureReview`。设置页的“进食线索”展示等待信号、轻提醒、等待首张、首图复核中、补充视角、取消、结束和暂停等真实状态；不会把转写原文或模型置信度塞进页面。

主屏只在有效轻提醒、拍摄窗口或首图复核存在时，安静显示一张小卡。提醒可收起；拍摄卡保留明确的“暂停拍照与识别”入口。有效期按服务端时间计算，即使轮询暂时断开，也会在到期时收起；离线状态不会把缓存窗口当作实时状态展示。没有相机心跳时明确写“等待相机连接”。

自动拍摄采用先取一张的 `probe` 阶段。首张到达后，`captureWindow` 可能已变为 null，页面仍根据 `captureReview.status=checking` 显示“首图复核中”。后端确认画面有食物后才显示 `followup`“补充视角”，清楚区分本阶段剩余张数与整轮最多 3 张。`waiting_retry` 优先于窗口 phase，仅显示“最多重试 1 张”，不会误称已经看到食物。无食物、无法确认或复核失败时结束小卡；“未见食物”不会显示成一餐。

设置的“自动拍照与识别”开关明确说明：开启后，线索触发的首张照片会发送到 Step 视觉检查，有食物才补充视角，实际食量仍由用户确认。此处沿用自动流程的产品授权，不增加弹窗。手动上传照片的分析仍使用单张选择入口。

有窗口的 `collecting` 场景在界面上表示“正在留意用餐线索”，不提前宣称照片已收好。线索本身不生成一餐，页面也不会填充餐食或热量。背屏仍只显示 IP 图案，不显示提醒摘要。演示模式不伪造真实本地语音或上下文信号。

## 背屏与原生桥

Habi 背屏采用 **17 × 23 单色点阵**、星形外轮廓与双白竖眼。唯一源 `contracts/rear-display/habi.json` 提供 6 状态、21 帧，React 预览和 Android 公共 Display 渲染直接读取同源数据；`rear-display-frames.json` 是可校验的文档导出。bit16 是 x=0，bit0 是 x=16。`idle / collecting / received / listening / watering / resting` 分别表示陪伴、留意、收好照片、聆听、轻摆、休息；休息不动，收到照片单次动作后停回静态。两端支持减少动画并清理定时器。

预览明确标注“设计预览、非实机回读”，可切换六种状态，不显示个人信息或文章摘要。真机 PZ261A 的点阵并非公共 Android Display，厂商写帧权限为 `signature|privileged`，当前开发包未获权限、设备没有可用 su。本轮已把共享帧打进实际安装的 APK，并读回 `vendor_permission_granted=false`、`native_rendering=false`；未把网页预览或厂商内置动画冒充自有 Habi 图案上屏。物理背屏的自定义帧接入仍需厂商授权与实际显示验收。

直接调取系统已有动作是另一条已验证路径：USB/ADB relay 只请求 `listening` 等具名状态，不上传自定义帧。背面朝上时复测为 power on / applied listening，用户确认看到“两只会动的眼睛”；随后按系统30秒超时熄屏、恢复默认待机。现有 relay 可继续跟随 Habi 状态。系统资源主要是眼睛表情，不是本页设计的星形全身；设置显示“内置动作联调”，背屏页分别标注系统动作连接和自定义图案接入。普通 APK 脱线独立调用仍未打通。

`device.rearDisplay=adb-relay` 时，设置页显示“电脑联调中”和 USB/电脑依赖；不宣称手机可独立运行。`window.EchoDevice.getCapabilities()` 与 `getStatus()` 用于只读能力及录音回读，每 2 秒及原生事件刷新。设备页展示 `recording.pipeline` 的本地 SenseVoice/Decider 阶段、处理计数、最近真实一句、线索动作及错误，没有数据时不补样本。开始/停止按钮分别调用 `startRecording()` / `stopRecording()`；开始的说明与权限由原生弹窗处理，accepted 只表示请求回执，不会将页面乐观改为录音中。演示不读取或展示真实录音状态，没有原生桥时不宣称录音已启用。录音实时状态不代表长时稳定性通过验收，背屏请求接受也不视为渲染成功。
